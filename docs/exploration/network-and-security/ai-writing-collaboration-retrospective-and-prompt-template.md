# AI 长文写作协作复盘与提示词模板

> 基于「网络安全入门三部曲」（三篇正文 12.5 万字 + 32 张图 + 一个入口页）的完整协作过程整理。
> 目的：把这次靠反复纠正才建立起来的标准，变成下次可以一次性交代清楚的东西。



## 一、最终定下来的基调（可直接复用）

分两类：**一开始就定、全程没改的**，和**靠纠正才确立的**。后者才是这次真正的收获。

### A. 一开始定下、全程未变的（自己一开始给的）

| # | 原则 | 说明 |
|---|---|---|
| A1 | **以防御/设计为主线，攻击只作动机引入** | 先讲"为什么会被打穿"，再讲"该怎么建"。防御部分要有独立篇幅，不是攻击的附属 |
| A2 | **面向"懂一点计算机、没系统学过本领域"的读者** | 不预设专业前置知识，需要的背景在文内从零讲起 |
| A3 | **循序渐进、生动有趣，但该较真处绝不含糊** | 允许比喻和幽默，不允许为了顺口牺牲准确 |
| A4 | **补充工业界现役方案 + 真实事故** | 原始材料只是骨架 |

### B. 靠纠正才确立的（AI 中途自由发挥的，然后纠正回来的点）

| # | 原则 | 起因 |
|---|---|---|
| **B1** | **每篇必须有叙事骨架，不能沿用原始材料的分类骨架** | 第二篇继承了课件的分类表，读起来像文件柜 |
| **B2** | **收尾必须提供新轴，不能复述正文** | 第二篇收尾被整节砍掉 |
| **B3** | **标题必须命名内容，不得描述作者动作或读者体验；不得含指示代词** | 三篇共改 46 处 |
| **B4** | **给未读者看的文字（钩子、导语、索引）不得要求任何前置知识** | 入口页两个钩子全部重写 |
| **B5** | **结论句去掉修辞后必须剩下可验证的事实** | 两句"金句"被判无效 |
| **B6** | **各篇篇幅需大致均衡，写前定上限** | 第二篇是第一篇的 2.6 倍 |



## 二、典型错误清单

### 错误 1：拿修辞冒充洞察

"攻击者不需要打破规则，他只需要满足规则"——对仗工整，但主语是错的（CSRF 里满足规则的是浏览器，不是攻击者）。

**自检**：把加粗、对仗、破折号全部去掉，看还剩什么。剩不下可验证的事实，就是在用句式充数。

### 错误 2：修一次不彻底

- 去课程化：先只改了第二篇，用户才要求第一篇
- 标题规范：先只改了第三篇被点名的 3 处，用户要求全量后才改 22 处；改完仍残留指示代词，第三轮才清干净

**根因**：改的是"被点名的实例"，不是"这一类问题"。而且检测规则本身有盲区（第一轮的正则只查连词开头、过短、内嵌标记，**唯独漏了指示代词**）。

**对策**：确认一类问题后，第一件事是**写出检测规则并全量扫描三篇**，而不是逐处手改。

> 我觉得全量扫描后也不一定真就不返工，这也受当时上下文环境影响，不止是提示词规不规范的问题，还需要有好的上下文管理习惯，尽量确保对话节奏的干净，少残留一些无关 Token 在上下文里。

### 错误 3：换一种表达方式才暴露的事实错误

TTL 绕过防火墙那个例子，方向写反了（`TTL = 16` 被标成"TTL 大"，而 16 < 22），**纯文字校对了三轮都没发现，画图时被迫问"到底哪份包先死"才暴露**。

**教训**：图不只是配图，它是一种**校验手段**。抽象描述可以含糊，坐标和箭头不行。

### 错误 4：排版层面的机械缺陷

重复标题（两个「防御思路」、两个「定义」）、多余星号、标题内嵌加粗、标题带 emoji、引号中西混用。

这些不需要判断力，纯粹是没做机械检查。**每次交付前脚本扫一遍即可，成本几乎为零。**





## 三、AI 在长对话中容易丢失的

按丢失概率排序：

1. **上一篇确立的语气标准**（最高）。第一篇干净，第二篇就开始敲黑板、引课程。**每开新一篇，先复述一遍禁令。**

2. **篇幅纪律**。材料多的时候会不自觉写长。**开写前逼 AI 说出目标字数。**

3. **把规则应用到"没被点名"的地方**。AI 倾向于只修被指出的实例。**每次纠正后追一句"其余篇目扫了吗"。**

4. **给未读者看的文字**。写惯了正文之后，AI 会用正文的手感写导语和钩子。**这类文字单独提醒一次。**

   > 我先写完三篇正文后，才回来做总结写入口介绍页，AI 反而顺着之前的上下文和思路，把他写成类似学后感了。

5. **机械排版一致性**。**交付可前跑脚本。**

**每交付一篇，让 AI 先自查**。第三篇是 AI 自己扫出 12 处元评论清理后才交的，那一轮的返工明显少于第二篇。



## 四、可复用的初始提示词模板

> 将这次的操作复刻成一个提示词模板，以后遇到类似任务时，可以直接从这参照。
>
> 有必要的话，可以将一些通用的，进一步整理成 SKill。

```
# 任务
把 <材料来源> 整理成一套 <N> 篇的技术博客。

# 读者
<懂一点 X、但没系统学过 Y 的人>。不预设专业前置知识，需要的背景在文内从零讲起。

# 内容原则
1. 以防御/设计为主线，攻击或问题只作为动机引入。
2. 原始材料只是骨架。要补充：该领域工业界现役方案、经典真实事故。
3. 补充内容用统一方框标出：> **📦 扩展知识：…** / > **📦 现实案例：…**

# 写作禁令（重要，每篇都适用）
1. 【禁止归因原始材料】正文中不得出现"课上说""教材写道""讲义里提到"等表述。
   你是作者，不是转述者。原始材料的观点直接以你自己的口吻断言。
2. 【禁止元评论】不得出现"请记住""请注意""值得你""强烈建议""刻在脑子里"
   "本篇的主线是""这一点极其重要"等敲黑板的话。让重要性从内容本身浮现。
3. 【禁止口号式结论】任何加粗的结论句，去掉修辞后必须剩下可验证的事实。
   对仗工整但经不起推敲的句子一律不要。
4. 【禁止复述式收尾】收尾必须沿一条正文没用过的新轴重新组织材料，
   不得把正文说过的话再列一遍。做不到就不写收尾。

# 结构要求
1. 每篇必须有自己的叙事骨架（一条线索/一个递进），
   不得直接沿用原始材料的分类结构。开写前先告诉我这一篇的骨架是什么。
2. 标题规范：
   - 标题必须命名内容，不得描述你的动作（"先说清楚…""我们一起来…"）
     或读者体验（"一个漂亮的…""值得一讲的…"）
   - 不得含指示代词（"这条""那个""它的"）——目录是脱离上下文被扫的
   - 同级标题句式统一；全文不得有重复标题；标题内不得嵌加粗或 emoji
   - 检验：把标题单独抽出来，不看正文能否知道这节讲什么
3. 给未读者看的文字（导语、钩子、索引、摘要）不得要求任何前置知识。
   悖论和张力必须用大白话就能感受到。

# 篇幅
每篇正文 <M> 字上下，最多不超过 <M×1.3>。各篇需大致均衡。
超了先自己砍，砍不动再来找我商量。

# 工作流
1. 先给我每篇的骨架和字数预算，我确认后再动笔。
2. 一次只写一篇，交付后等我反馈，再写下一篇。
3. 每篇交付前自查：按上面全部禁令逐条扫一遍，把命中数报给我。
4. 我指出某一类问题后，你要先写出检测规则、全量扫描所有篇目，
   再统一修改——不要只改我点名的那几处。
5. 正文定稿后再配图。
```

### 配图阶段追加提示

```
# 配图
1. 时序、流程、状态机 → Mermaid 代码块
   拓扑、结构、报文布局、对照表 → 内联 SVG
   字节偏移、对齐类 → 代码块内的字符图
2. SVG 用 <目标平台> 的主题变量（如 VitePress 的 --vp-c-text-1、--vp-c-brand-soft），
   带 fallback 值，保证明暗主题自动跟随。
3. 每张图配一句图注，图注要给出正文没说的观察角度，不要复述图里已有的内容。
4. 密度参考：每 3000～4000 字一张。
5. 画图时如果发现正文的描述无法落成确定的坐标或箭头方向，
   立刻停下来告诉我——那通常意味着正文有事实错误。
```

## 五、一句话总结

这次协作里，**真正省时间的不是把要求说得更细，而是把要求变成可以被机械检查的东西**。

"语气要自然"是没法核对的；"不得出现『请记住』"可以一秒扫完。
**把口味判断、更多变的东西留给对话，把可判定的规则写成清单**——这是下次能少绕七八轮的主要来源。
